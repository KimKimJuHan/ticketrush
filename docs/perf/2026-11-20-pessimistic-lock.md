# 부하 테스트: 잠금 없음 vs 비관적 락

- 날짜: 2026-11-20
- 대상: `feat/pessimistic-seat-lock` 브랜치 (설정 `ticketrush.hold.locking`으로 두 방식을 같은 코드에서 전환)
- 시나리오와 환경: [기준선 리포트](2026-11-19-hot-seat-baseline.md)와 같음 (1,000명, 좌석 100석, 같은 PC, 앱 CPU 2개, 커넥션 풀 10)
- 실행: `./loadtest/run.ps1 -Locking none -Warmup`, `./loadtest/run.ps1 -Locking pessimistic -Warmup`

## 요약

- **거짓 성공이 0이 됐다.** 비관적 락으로 3회 실행했을 때 선점 성공 응답은 매번 정확히 100건(좌석 수와 같음)이었고, 예매 단계의 `NOT_HOLDER`는 0건이었다. 같은 날 잠금 없이 실행한 2회에서는 6명, 10명이 거짓 성공을 받았다.
- **응답시간은 거의 달라지지 않았다.** 앱을 띄운 뒤 같은 순번의 실행끼리 비교하면 선점 p95가 3,596ms(잠금 없음)와 3,600ms(비관적 락)로 같았다.
- **행 잠금 대기는 병목이 아니었다.** 좌석 행 잠금 대기 시간은 평균 14ms, 최대 99ms였다. 같은 시간 DB 커넥션 획득 대기는 최대 3.0초였다. 응답시간을 정하는 것은 여전히 커넥션 풀과 CPU다.

## 결과

### 정합성

| 실행 | 잠금 | 선점 성공 응답 | 예매 성공 | 거짓 성공 | 정합성 4항목 |
| --- | --- | --- | --- | --- | --- |
| 워밍업 | 없음 | 106 | 100 | **6** | PASS |
| 측정 | 없음 | 110 | 100 | **10** | PASS |
| 1회 (워밍업 없이) | 비관적 | 100 | 100 | **0** | PASS |
| 워밍업 | 비관적 | 100 | 100 | **0** | PASS |
| 측정 | 비관적 | 100 | 100 | **0** | PASS |

비관적 락에서는 선점 성공 응답 수가 좌석 수를 넘지 않는다. 같은 좌석에 대한 두 번째 요청은 첫 번째 트랜잭션의 커밋을 기다린 뒤 HELD가 된 값을 읽고 409로 거절된다. 이 동작은 통합 테스트(`SeatHoldConcurrencyTest`: 20명 동시 선점 시 정확히 1명 성공, 반대 순서 요청 시 교착 상태 없음)로도 고정했다.

### 응답시간

앱 컨테이너를 새로 띄운 뒤 몇 번째 실행인지에 따라 p95가 크게 달라진다(JIT 워밍업, 기준선 리포트 3절). 그래서 **같은 순번끼리** 비교한다. 두 방식 모두 잠금 설정을 바꾸면서 앱 컨테이너가 새로 만들어졌다.

| 앱 기동 후 순번 | 잠금 없음 p95 (조회 / 선점 / 예매) | 비관적 락 p95 (조회 / 선점 / 예매) |
| --- | --- | --- |
| 1번째 | 5,793 / 6,196 / 5,329ms | 5,709 / 6,413 / 5,663ms |
| 2번째 | 2,002 / 3,596 / 3,087ms | 1,953 / 3,600 / 3,073ms |
| 3번째 | (측정 안 함) | 1,602 / 2,704 / 2,350ms |

같은 순번끼리의 차이는 1번째 실행에서 1~6%, 2번째 실행에서 1% 이내다. 순번이 하나 바뀔 때의 차이(40~60%)보다 훨씬 작다. 비관적 락이 응답시간을 늘린다는 근거는 이번 측정에서 나오지 않았다.

### 대기 시간 분해 (Prometheus)

| 지표 | 잠금 없음 (2번째) | 비관적 락 (2·3번째 구간) |
| --- | --- | --- |
| 좌석 행 읽기·잠금 시간 최대 (`ticketrush_seat_lock_wait_seconds_max`) | 294ms | 99ms |
| 좌석 행 읽기·잠금 시간 평균 (기동 후 누적) | | 14ms (3,298회) |
| 커넥션 획득 대기 최대 (`hikaricp_connections_acquire_seconds_max`) | 5.7초 | 3.0초 |

잠금 없음에서도 좌석 읽기 시간이 수백 ms까지 늘어난 것은 잠금 때문이 아니라 CPU 포화로 쿼리 처리 자체가 밀렸기 때문으로 본다.

## 분석: 왜 비관적 락이 느려지지 않았나

ADR-0004에서는 비관적 락의 단점을 "대기 증가, 커넥션 점유"로 예상했다. 이번 조건에서 그 비용이 드러나지 않은 이유는 두 가지다.

1. **잠금을 쥐는 시간이 짧다.** 선점 트랜잭션은 좌석 행을 읽고 바꾸고 커밋하는 짧은 작업이라 행 잠금이 수 ms만 유지된다. 기다리는 쪽도 잠깐만 기다린다.
2. **커넥션 풀이 동시 실행 수를 이미 10으로 제한한다.** 1,000개 요청이 들어와도 DB에서 동시에 트랜잭션을 여는 것은 최대 10개다. 같은 좌석의 잠금을 기다리는 트랜잭션도 최대 9개뿐이다. 대부분의 대기는 잠금에 닿기 전, 커넥션을 받는 단계에서 이미 일어난다.

즉 현재 병목은 "좌석 행 경합"이 아니라 "커넥션 풀과 CPU"다. 비관적 락의 대기 비용은 풀을 늘리거나, 한 좌석에 경합이 더 몰리거나(`-HotSeats 10`), 트랜잭션 안에서 외부 호출처럼 오래 걸리는 작업을 할 때 드러날 가능성이 크다.

## 한계

- 잠금 없음은 워밍업 후 1회, 비관적 락은 워밍업 포함 3회 측정했다. 응답시간 비교는 같은 순번 2쌍(1번째, 2번째)에 근거한다.
- 부하 발생기와 앱이 같은 PC에서 돈다. 절대값보다 같은 날·같은 조건의 상대 비교로 읽는다.
- 행 잠금 대기 지표는 이번 PR에서 추가했다. 기준선(11/19) 실행에는 이 지표가 없다.

## 결정과 다음 단계

- 운영 기본값을 비관적 락으로 정했다 ([ADR-0007](../adr/0007-pessimistic-seat-lock.md)).
- 응답시간 SLO(p95 500ms)는 여전히 미달이다. 다음 개선 대상은 잠금 방식이 아니라 **커넥션 풀 크기·트랜잭션 범위·CPU**다. AWS 단계에서 부하 발생기를 분리한 뒤 다시 측정한다.
- 경합을 극단적으로 높인 조건(`-HotSeats 10`)과 낙관적 락·조건부 UPDATE 비교는 필요해지면 같은 시나리오로 추가한다.
