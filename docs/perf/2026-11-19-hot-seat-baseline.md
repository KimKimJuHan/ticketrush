# 부하 테스트 기준선: 핫시트 (락 없음)

- 날짜: 2026-11-19
- 대상 커밋: `9d53ea4` (좌석 선점에 동시성 제어 없음, ADR-0004)
- 시나리오: [`loadtest/scenarios/hot-seat.js`](../../loadtest/scenarios/hot-seat.js), 실행 `./loadtest/run.ps1`

## 요약

1,000명이 같은 순간에 좌석 100석을 선점하고 예매하도록 5회 실행했다.

- **중복 판매는 0건이었다.** 5회 모두 정합성 검사 4항목을 통과했다. DB의 부분 유니크 인덱스(ADR-0003)와 예매 단계의 선점자 확인이 동작했다.
- **거짓 성공은 매회 1~9명 발생했다.** "선점 성공(201)" 응답을 받았지만 선점이 다른 사용자에게 덮어써져, 예매 단계에서 403 `NOT_HOLDER`로 거절된 사용자다. 5회 합계는 25명이고, 선점 성공 응답의 4.8%(25/525)에 해당한다.
- **응답시간 SLO는 모두 미달했다.** 선점 p95는 2.0~5.1초로 목표(500ms)의 4~10배였다. 대부분은 쿼리 실행이 아니라 **DB 커넥션 대기**에 쓰였다.

## 측정 환경

| 항목 | 값 |
| --- | --- |

| 부하 | VU 1,000개가 각 1회씩: 배치도 조회 → 선점 → 0.3~1.0초 대기 → 예매. 로그인을 마친 뒤 같은 시각에 동시 출발 |

## 분석

### 1. 거짓 성공이 생기는 경로

선점은 "읽기 → 판단 → 쓰기"가 락 없이 이뤄진다(ADR-0004). 두 요청이 같은 좌석을 동시에 AVAILABLE로 읽으면 둘 다 판단을 통과하고, 나중에 커밋한 쪽이 `held_by_user_id`를 덮어쓴다. 두 사용자 모두 201을 받지만 실제 선점자는 한 명이다. 먼저 커밋한 사용자는 결제 단계에서 처음으로 좌석을 잃은 사실을 알게 된다.

판매 단계는 선점자 확인(`isHeldBy`)과 DB 유니크 인덱스로 이중 방어되어 있어 중복 판매로 이어지지는 않았다. `DB 방어선 작동`이 0이라는 것은 이번 부하에서는 애플리케이션 검사만으로 막혔고, 최종 방어선까지 갈 일이 없었다는 뜻이다.

거짓 성공 수가 1~9명으로 적은 이유는 경합 구간이 짧기 때문이다. 1,000명이 100석에 고르게 흩어지므로 좌석당 경쟁자는 평균 10명이고, 대부분은 이미 HELD로 바뀐 좌석을 읽어 409를 받는다. 덮어쓰기는 두 트랜잭션의 "읽기~커밋" 구간이 겹칠 때만 생긴다. `-HotSeats 10`처럼 좌석을 좁히면 경합이 커진다(다음 실험).

### 2. 응답시간: 커넥션 풀 대기가 지배적

| 관찰 (1~5회 중 최대값) | 값 |
| --- | --- |
| HikariCP 활성 커넥션 | 10 / 10 (항상 포화) |
| 커넥션을 기다린 요청 수 | 최대 185 |
| 커넥션 획득 시간 | 최대 4.1초 |
| 앱 프로세스 CPU | 98% (2코어 기준) |
| GC 정지 | 최대 0.12초 (Serial GC) |
| 힙 사용량 | 최대 약 150MB / 1GB |

요청이 순간적으로 1,000개 들어오는데 DB 커넥션은 10개뿐이라, 대부분의 요청이 커넥션을 기다리는 데 시간을 썼다. 커넥션 획득 대기의 최대값(4.1초)이 가장 느린 회차의 선점 p95(5.1초)와 같은 수준이다. CPU도 포화 상태여서, 커넥션 수만 늘리면 대기 위치가 풀에서 CPU(앱과 PostgreSQL)로 옮겨갈 가능성이 크다. GC와 힙은 병목이 아니었다.

### 3. 회차가 갈수록 빨라진 이유

앱은 5회 내내 재시작되지 않았다. 다만 1회차는 앱이 뜬 뒤 로그인·선점·예매 코드가 **처음** 실행된 회차였고, 시드 볼륨 설정 변경으로 PostgreSQL 컨테이너도 직전에 다시 만들어졌다. 선점 p95는 5.1초 → 3.1초 → 2.4초 → 2.1초 → 2.0초로 줄다가 안정됐다. JIT 컴파일러가 자주 실행되는 코드 경로를 기계어로 최적화하는 효과(워밍업)와 DB 캐시가 채워지는 효과가 겹친 것으로 본다. **이후 비교는 워밍업 실행 1회 후의 측정값으로 한다.**

## 한계

- 부하 발생기와 앱이 같은 PC에서 돈다. k6의 `http_req_connecting` p95가 약 1초로, 동시 연결 1,000개를 여는 비용도 응답시간에 섞여 있다.
- 실행마다 무작위로 좌석을 고르므로 거짓 성공 수의 편차가 크다(1~9). 개선 효과는 여러 회차의 합계나 평균으로 비교한다.

## 다음 단계

1. **좌석 선점 동시성 제어**: 비관적 락(`SELECT ... FOR UPDATE`), 조건부 UPDATE(`WHERE status='AVAILABLE'`), Redis 분산 락을 같은 시나리오로 비교한다. 목표는 거짓 성공 0명이다.
2. **커넥션 풀·트랜잭션 범위 조정**: 풀 크기를 바꿔 가며 p95와 CPU를 함께 측정하고, 트랜잭션 안에서 커넥션을 붙잡는 시간을 줄인다.
3. **경합 강도 변경**: `-HotSeats 10`으로 같은 측정을 반복한다.
4. **AWS 분리 측정**: 부하 발생기를 별도 인스턴스로 옮겨 클라이언트 쪽 비용을 제거한다.
