# ADR-0007: 좌석 상태 변경은 비관적 락으로 보호한다

- 상태: 채택
- 날짜: 2026-11-20
- 대체: [ADR-0004](0004-hold-in-db-first.md)의 "MVP는 락 없이" 결정

## 배경
기준선 측정([리포트](../perf/2026-11-19-hot-seat-baseline.md))에서 1,000명이 좌석 100석에 동시에 몰리면, 실행마다 1~10명이
"선점 성공" 응답을 받고도 좌석을 빼앗겼다(거짓 성공). 원인은 선점이 "읽기 → 판단 → 쓰기"를 잠금 없이 해서, 동시에 읽은 두 요청 중
나중에 커밋한 쪽이 먼저 쓴 선점자를 덮어쓰는 Lost Update다. 중복 판매는 DB 제약조건(ADR-0003)이 막았지만, 사용자는 결제 단계에서야
실패를 알게 된다.

## 결정
- 선점, 선점 해제, 예매 확정은 모두 `SeatLocker`를 통해 좌석을 읽고, 운영 기본값은 **비관적 락**(`SELECT ... FOR UPDATE`)이다.
  - 예매 확정도 잠그는 이유: 선점이 만료되는 순간 다른 사용자의 새 선점과 이 예매가 같은 행을 동시에 바꿀 수 있다.
- 여러 좌석은 항상 **좌석 ID 오름차순**으로 잠근다. 요청 순서대로 잠그면 [1, 2]와 [2, 1] 요청이 서로를 기다리는 교착 상태가 생긴다.
- 잠금 방식은 설정값 `ticketrush.hold.locking`(`pessimistic` | `none`)으로 바꿀 수 있다. `none`은 기준선을 같은 코드로 재현해
  비교하기 위한 실험용이며, 앱 기동 시 경고 로그를 남긴다. 실행 중인 값은 `/actuator/info`로 확인한다.
- 좌석 행을 읽는(잠그는) 시간을 `ticketrush.seat.lock.wait` 지표로 남겨, 커넥션 대기와 행 잠금 대기를 구분한다.

## 근거 (측정, [리포트](../perf/2026-11-20-pessimistic-lock.md))
| 항목 | 잠금 없음 | 비관적 락 |
| --- | --- | --- |
| 거짓 성공 | 6, 10명 | 0, 0, 0명 |
| 선점 성공 응답 | 106, 110건 | 100, 100, 100건 (= 좌석 수) |
| 선점 p95 (앱 기동 후 2번째 실행) | 3,596ms | 3,600ms |
| 행 잠금 대기 | | 평균 14ms, 최대 99ms |

정합성 문제는 사라졌고, 응답시간 비용은 측정되지 않았다. 행 잠금은 수 ms만 유지되고, 커넥션 풀(10개)이 DB의 동시 트랜잭션 수를
이미 제한해서 한 행을 기다리는 트랜잭션도 많지 않기 때문이다.

## 검토한 대안
ADR-0004의 후보 중 이번에는 비관적 락만 구현·측정했다.

| 대안 | 이번에 택하지 않은 이유 |
| --- | --- |
| 낙관적 락 (`version` 컬럼) | 티켓 오픈처럼 한 행에 경합이 몰리면 대부분의 요청이 커밋 시점에 실패한다. 실패한 요청도 트랜잭션 전체 비용을 다 쓴 뒤다. 마이그레이션도 필요하다 |
| 조건부 UPDATE | 쿼리 한 번으로 원자적이지만, 여러 좌석을 "전부 아니면 전무"로 처리하려면 영향 행 수 검증과 롤백 처리를 따로 짜야 한다. 현재 측정으로는 비관적 락보다 나을 근거가 없다 |
| Redis 원자 연산 | 서버가 여러 대일 때 장점이 있지만, DB와 Redis 상태를 일치시키는 문제가 새로 생긴다. 지금은 서버 1대이고 병목도 행 경합이 아니다 |

같은 시나리오와 지표가 있으므로, 경합 조건이 바뀌거나 서버를 늘릴 때 같은 방식으로 다시 비교할 수 있다.

## 결과
- 선점 성공 응답은 실제 선점과 일치한다. 사용자가 결제 단계에서 좌석을 잃는 경우가 없어진다.
- 잠금을 기다리는 동안 DB 커넥션을 쥐고 있으므로, 커넥션 풀을 늘리거나 트랜잭션 안에 느린 작업을 넣으면 대기 비용이 커질 수 있다.
  선점·예매 트랜잭션 안에서 외부 호출(실제 결제 등)을 하지 않는다는 원칙을 유지한다.
- 잠금 대기 시간 상한(lock timeout)은 두지 않았다. 현재 잠금 유지 시간이 수 ms라 필요가 없지만, 결제 연동 등으로 트랜잭션이 길어지면 다시 검토한다.
- 응답시간 SLO 미달의 원인은 잠금이 아니라 커넥션 풀과 CPU다. 다음 개선은 그쪽을 대상으로 한다.

## 적용하면서 함께 고친 것
- **만료 선점 정리 작업과의 교착 상태.** 정리 작업(`ExpiredHoldCleaner`)은 `UPDATE ... WHERE status='HELD' AND hold_expires_at <= now`
  한 문장이었고, 만료 시각 인덱스 순서로 행을 잠갔다. 선점 트랜잭션은 ID 순서로 잠그므로 두 순서가 엇갈리면 교착 상태가 된다.
  PostgreSQL에서 재현했다(선점이 좌석 1을 쥐고 2를 기다리는 동안 정리 작업이 2를 쥐고 1을 기다려 `deadlock detected`).
  정리 쿼리도 `SELECT ... ORDER BY id FOR UPDATE`로 대상을 ID 순서로 먼저 잠근 뒤 바꾸도록 고쳤고, 같은 상황을 만드는 회귀 테스트를 추가했다.
  원칙: **같은 테이블의 행을 여러 개 잠그는 모든 경로는 같은 순서(좌석 ID 오름차순)를 따른다.**

## 알려진 한계 (이번 범위 밖)
- **1인 매수 제한의 동시 요청.** 잠금은 좌석 행에 걸리므로, 같은 사용자가 서로 다른 좌석을 동시에 여러 요청으로 선점하면
  각 요청이 서로의 선점을 보지 못하고 한도(`max_seats_per_user`)를 넘을 수 있다. 정상 사용자가 겪기는 어렵고 자동화된 요청에서
  생길 수 있다. 사용자·회차 단위 잠금(예: PostgreSQL advisory lock)으로 막을 수 있으며, 필요해지면 별도로 처리한다.
- **같은 Idempotency-Key로 동시에 들어온 예매.** 두 번째 요청은 첫 번째 요청의 좌석 잠금이 풀린 뒤 이미 SOLD가 된 좌석을 보고
  403 `NOT_HOLDER`를 받는다. 이전 결과를 그대로 돌려주는 동작은 요청이 순차적으로 재시도될 때만 보장된다.
