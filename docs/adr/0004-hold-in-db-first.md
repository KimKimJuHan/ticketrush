# ADR-0004: 좌석 선점은 먼저 DB에 단순하게 구현하고, 개선 방식은 측정 후 정한다

- 상태: 채택 (7~8주차 실험 결과에 따라 대체 예정)
- 날짜: 2026-10-30

## 배경
좌석 선점(AVAILABLE → HELD)은 동시 요청이 가장 몰리는 지점이다. 해결 방식은 여러 가지이고, 각각 성능·복잡도·정합성의 장단점이 있다.

## 결정
- 3~4주차 MVP에서는 `performance_seats` 행의 상태를 읽고 바꾸는 **가장 단순한 방식**으로, 락 없이 구현한다.
- 6주차에 부하 테스트로 문제(중복 선점)를 수치로 재현한다.
- 7~8주차에 아래 후보를 같은 시나리오로 측정한 뒤, 결과를 근거로 새 ADR을 쓴다.

| 후보 | 핵심 아이디어 | 예상 장점 | 예상 단점 |
| --- | --- | --- | --- |
| 비관적 락 (`SELECT ... FOR UPDATE`) | 읽는 순간 행을 잠근다 | 단순, 확실 | 대기 증가, 커넥션 점유 |
| 낙관적 락 (`version` 컬럼) | 바꿀 때 버전이 그대로인지 확인 | 경합이 적을 때 빠름 | 경합이 많으면 실패·재시도 폭증 |
| 조건부 UPDATE | `UPDATE ... WHERE status = 'AVAILABLE'`의 영향 행 수로 판단 | 쿼리 한 번으로 원자적 | 여러 좌석 동시 선점 처리 주의 |
| Redis 원자 연산 | `SET NX` + TTL로 선점, 만료 자동 | DB 부하 감소, TTL로 만료 처리 | DB와 Redis 간 정합성 관리 필요 |
| 대기열 | 입장 인원 자체를 제한 | 시스템 보호 | 구현 복잡, 대기 경험 |

※ "예상" 열은 가설이며, 실험 후 실제 수치로 대체한다.

## 결과
- 처음부터 정답을 고르는 대신, 문제를 재현하고 비교한 과정 자체가 포트폴리오의 핵심 근거가 된다.
- MVP 단계의 선점 코드는 의도적으로 안전하지 않다. 이 사실을 코드 주석과 README에 명시해 오해를 막는다.
