# ADR-0006: 부하 테스트는 k6로 하고, 응답 지표와 DB 정합성을 함께 판정한다

- 상태: 채택
- 날짜: 2026-11-19

## 배경
ADR-0004에서 좌석 선점은 일부러 동시성 제어 없이 구현했다. 이후 락 전략을 비교하려면 먼저 같은 조건에서 반복 가능한
기준선이 필요하다. 이 기준선은 "동시에 몰렸을 때 몇 명이 거짓 성공 응답을 받는가"와 "응답시간 SLO를 지키는가"를
숫자로 보여 줘야 한다.

부하 테스트 도구는 응답 코드와 응답시간만 볼 수 있다. 중복 판매처럼 DB에 남는 문제는 테스트가 끝난 뒤
DB를 직접 조회해야 확인할 수 있다.

## 결정
- 부하 발생기는 **k6**를 쓴다. 시나리오를 JavaScript 코드로 작성해 리포에서 리뷰·버전 관리한다.
- k6는 `deploy/local/compose.yaml`의 `loadtest` profile로 **Docker 이미지(버전 고정)**를 실행한다. 별도 설치가 필요 없다.
- 판정은 세 가지를 함께 본다.
  1. **응답**: k6 threshold (p95 SLO, 예상 밖 응답 0건, 거짓 성공 0건)
  2. **서버 내부**: Prometheus·Grafana (ADR-0005). k6도 remote write로 클라이언트 측 지표를 같은 Prometheus에 보낸다.
  3. **DB 상태**: 테스트 직후 `loadtest/seed/verify.sql`로 중복 판매, 상태 불일치, 결제 누락을 검사한다.
- 시드는 매번 모든 테이블을 비우고 같은 데이터를 만든다. 실행 간 차이는 코드 변경에서만 생기게 한다.
- 선점 경쟁 패배(409)와 빼앗긴 선점으로 인한 예매 거절(403 `NOT_HOLDER`)은 측정 대상이므로 실패율에서 제외하고, 에러 코드별 커스텀 카운터로 센다.

## 검토한 대안
| 대안 | 기각 이유 |
| --- | --- |
| JMeter | GUI로 만든 XML 시나리오라 코드 리뷰와 diff가 어렵다. 스레드 기반이라 같은 PC에서 VU 1,000개를 띄우기 무겁다 |
| Gatling | 시나리오를 코드로 관리할 수 있지만 Scala·Java DSL과 빌드 설정이 추가로 필요하다. 이 규모에는 과하다 |
| nGrinder | 컨트롤러·에이전트 서버를 따로 운영해야 한다. 1인 프로젝트의 로컬 반복 실험에 맞지 않는다 |
| 애플리케이션 통합 테스트로 동시성 재현 | 정합성 확인에는 좋지만 HTTP·커넥션 풀·스레드 풀을 거치는 실제 응답시간을 볼 수 없다 |

## 결과
- `./loadtest/run.ps1` 한 번으로 시드 → 부하 → 검증이 반복 가능하게 실행된다.
- 로컬에서는 k6와 앱이 CPU를 나눠 쓰므로 절대 수치보다 **같은 환경에서의 전후 비교**에 의미가 있다.
  AWS 단계에서는 부하 발생기를 별도 인스턴스로 분리한다.
- 측정 결과는 `docs/perf/`에 날짜별 리포트로 남기고, 원시 결과 JSON(`loadtest/results/`)은 리포에 올리지 않는다.
